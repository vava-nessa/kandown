# Interactive demo — run the real app on kandown.dev, wiped on reload

## Context

The website has no way to *try* Kandown. A screenshot or a recorded video proves
nothing about a tool whose whole pitch is "it is just files you can move around".
Visitors should be able to drag a card, open the drawer, edit markdown, and see
the file change — from a link, with no install.

The constraint that makes this worth doing properly: **the demo must be built
from the real application**, not reimplemented. A hand-written mock drifts within
two releases and then actively lies about the product.

### What the codebase already gives us

The web UI has exactly one I/O choke point. `src/lib/filesystem.ts` already
supports two backends:

| Mode | Trigger | How it reads/writes |
|---|---|---|
| Picker | default | File System Access API, `FileSystemDirectoryHandle` |
| Server | `window.__KANDOWN_ROOT__` set | REST `/api/*` through `apiFetch()` |

Every server-mode call — board, config, instructions, task list, task CRUD,
archive/unarchive, migrate, daemon, update — funnels through the single
`apiFetch(path, options)` helper (`src/lib/filesystem.ts:116`). The REST contract
is already written down twice, in `vite.config.ts` (`kandownDevPlugin`) and in
`src/cli/lib/server.ts`.

**So the demo is a third backend that answers the same REST calls from memory.**
One branch in `apiFetch`, and the ~50 `isServerMode()` guard sites scattered
through `store/*.ts` keep working untouched.

## Design decisions

### Storage: in-memory, not localStorage

The requirement is "reload wipes everything". `localStorage` **survives** reload —
it would need explicit clearing on every boot, which is the same behaviour with
extra failure modes (quota errors, cross-tab bleed, leftover data on the
visitor's `kandown.dev` origin if the clearing code ever throws).

A plain `Map<string, string>` seeded at module init gives the reset for free:
reload re-runs the module, the old map is garbage. No quota, no privacy
footprint, no cleanup code that can fail.

Corollary: **IndexedDB must be stubbed in demo mode.** `saveRecentProject` /
`listRecentProjects` currently write to IndexedDB. On kandown.dev that would
leave real data in the visitor's browser. They become no-ops.

### Bundle: a separate demo build, tree-shaken out of the shipped CLI

The demo backend and its seed dataset must not bloat the 6.2 MB single-file
bundle that every `npx kandown` user downloads. Gate them behind a compile-time
constant so Rollup drops them from the normal build:

- `vite build --mode demo` → `define: { __KANDOWN_DEMO_BUILD__: true }`
- normal build → `false`, and the entire `demoBackend` import is eliminated

The demo build also **turns off `viteSingleFile`**. Single-file exists so the CLI
can serve one asset from disk; on the website we control hosting, so a normal
chunked build with a hashed asset graph loads far faster than 6.2 MB of inline
base64.

### Freshness: built from the repo, at website build time

`website/scripts/build-demo.mjs` runs before the site build:

1. Default — build the sibling checkout (`pnpm --dir .. build:demo`) and copy
   `dist-demo/` → `website/public/demo/app/`. Vercel clones the whole repo, so
   this works there as well as locally, and it always matches HEAD.
2. Fallback (`--from-npm`, or when the sibling has no `package.json`) — download
   the `kandown@latest` tarball and extract the demo build from it. Useful for
   building the site outside the monorepo.

Either way the script writes `website/src/generated/demo-meta.json`
(`{ version, builtAt, source }`) so the demo page can display which version is
running, and so a stale demo is visible rather than silent.

## Subtasks

- [x] **Demo backend** — add `src/lib/demoBackend.ts`: an in-memory virtual
      filesystem (`Map<string, string>`) plus a `demoApi(path, options): Promise<Response>`
      router implementing the same routes as `kandownDevPlugin` in `vite.config.ts`:
      `GET/PUT /api/config`, `GET/PUT /api/board`, `GET/PUT /api/instructions`,
      `GET /api/tasks`, `GET/PUT/DELETE /api/tasks/:id`,
      `POST /api/tasks/:id/archive|unarchive`. Return real `Response` objects so
      `apiFetch`'s error handling is exercised unchanged. Routes that cannot
      exist in a browser (`/api/daemon`, `/api/update/*`, `/api/tasks/:id/agent`,
      `/api/migrate-tasks`) return a documented 501 rather than throwing.

- [x] **The flag** — `window.__KANDOWN_DEMO__` + `isDemoMode()` in
      `filesystem.ts`. `isServerMode()` returns true in demo mode: its real
      meaning is "a managed backend answers `/api/*`", and an in-process backend
      qualifies. Update its JSDoc to say so, so the next reader is not misled.
      Then a single branch at the top of `apiFetch`:
      `if (isDemoMode()) return demoApi(path, options)`.

- [x] **Watcher + IndexedDB** — skip the watcher entirely in demo mode and stub
      the three recent-project functions to no-ops.
      report: Turned out `setupWatcher` never reaches the SSE path in server mode — it
      installs a 2s poll and returns. That poll is what needed disabling: with the
      store as the only writer, it burned a full board reload every 2s to discover
      our own changes, and the re-render could land mid-drag.

- [x] **Seed dataset** — a believable small project across all five columns.
      report: Nine tasks in `src/lib/demoSeed.ts` as TypeScript constants, not
      `templates/demo/*.md` behind `import.meta.glob`. The glob is transformed at
      build time regardless of whether the guarded branch survives, so it risked
      shipping the dataset to CLI users; constants tree-shake with certainty.
      Covers a dependency gate (t2 → t5), an AI-owned card with a `report:` block,
      an archived task, and a body-only search word.

- [x] **In-app demo affordances** — suppress what cannot work without a disk.
      report: Less was needed than planned. The CLI-only surfaces already hide
      themselves: `/api/daemon` returns 501, and the UI treats a failed daemon call
      as "no daemon", so the agent button and updater never appear. `EmptyState`
      is never reached because the demo auto-opens its project. The one real fix
      was the onboarding tour, which would have reappeared on every reload. The
      DEMO badge lives in the site chrome above the iframe rather than in the app.

- [x] **Demo build target** — `pnpm build:demo` script, `mode: 'demo'` handling in
      `vite.config.ts` (define the constant, drop `viteSingleFile`,
      `outDir: 'dist-demo'`, `base: '/demo/app/'`, inject
      `window.__KANDOWN_DEMO__ = true` via `transformIndexHtml`). Verify with
      `pnpm build` that the normal single-file bundle does **not** contain the
      seed data or the demo router.

- [x] **Website: build script** — `website/scripts/build-demo.mjs` as specified
      above, wired into `prebuild` (and `predev`, skipped if the output already
      exists so `pnpm dev` stays fast). Add `public/demo/` to
      `website/.gitignore`.

- [x] **Website: `/demo` route** — `website/src/routes/demo.tsx`. Full-bleed
      `<iframe src="/demo/app/index.html">` under a slim editorial bar: the DEMO
      flag, the running version from `demo-meta.json`, a "reload to reset"
      note, and an `npx kandown` copy button as the exit ramp. The iframe loads
      only after an explicit click on the page (or immediately on `/demo`, but
      never preloaded from the landing page — it is megabytes).

- [x] **Website: entry points** — hero link, header link, headers, caching.
      report: The ⌘K conflict does not exist — key events inside an iframe stay in
      the frame's own window and never reach the parent's listener, so both
      palettes coexist. What did need fixing was `X-Frame-Options: DENY`, which
      blocks same-origin framing too; relaxed to `SAMEORIGIN`. Also pinned the
      demo page to the viewport and dropped the site footer on `/demo`, or the
      outer page scrolled behind the app and produced two scrollbars.

- [x] **Docs** — a `Try it` callout in `docs/introduction`, a section in
      `website/README.md`, a `CHANGELOG.md` entry, JSDoc headers on every new file
      and a regenerated `CODEMAP.md`.

## Outcome

Live at `/demo`. The board renders eight seeded tasks across five columns, the
drawer reads task bodies from memory, the archive filter and the dependency gate
both work, and a raw `fetch('/api/tasks')` from inside the frame returns 404 —
the app never touches the network. Storage stays empty in both the page and the
frame; a reload puts everything back.

## Follow-ups

- **Bundle weight.** The demo's main chunk is 2.49 MB / 730 kB gzip, against
  6.2 MB for the single-file CLI build. Acceptable behind an explicit click, but
  BlockNote is the obvious next split — it is only needed once a drawer opens.
- **Behaviour drift.** The REST contract is now written three times: the CLI
  server, `kandownDevPlugin`, and `demoBackend`. `DEMO_SUPPORTED_ROUTES`
  documents the third; extracting a shared literal all three consume would make
  divergence impossible rather than merely visible.
- **A reset button.** `resetDemoBackend()` exists and is unwired. Re-seeding
  without a full page reload would be a better exit from a demo the visitor has
  made a mess of.
