# Markdown code blocks always readable (contrast safety)

## Context

BlockNote renders fenced code blocks with the Shiki highlighter (github-light
in light mode, github-dark in dark mode). The previous styling in
`src/styles/globals.css` forced the `pre` background to `hsl(var(--muted))`
and the text to `hsl(var(--foreground))` with `!important`, but Shiki injects
its token colors as inline `style="color: #xxx"` on `<span>` elements, which
wins over external CSS. The result: spans render with Shiki's token colors on
top of the muted background, and:

- `--muted` can be too close in lightness to either Shiki palette on certain
  themes (notably community themes with tinted backgrounds), so the code reads
  as low-contrast / "foggy".
- The monospace font is not forced — BlockNote inherits whatever the wrapper
  provides, which is the sans font for some themes.
- The contrast is not a property the theme system exposes, so a theme author
  has no way to fix it from JSON.
- Inline `code` (single backticks) inside markdown is not styled, so a
  backticked token in body prose can disappear against the surrounding text.
- The theme customizer preview does not show what a code block looks like, so
  authors ship unreadable palettes without seeing the breakage.

## Goal

Make every fenced code block in the task description, subtask description and
report editor (BlockNote), plus any markdown rendered through the Tailwind
`prose` class, guaranteed readable on every theme, with a monospace font
forced and the `kandown` palette providing safe defaults that community
themes can extend.

## Decisions

- **Keep Shiki's github-light / github-dark palette** rather than
  monochrome or themed tokens — the Shiki colors are well-curated for
  readability on white / `#0d1117`. We only need the *background* to match
  the active mode, which the new `code-bg` token provides.
- **One token per slot, mode-aware** — `code-bg` is a single CSS variable
  that holds the right value for the resolved mode (set by
  `applyProjectTheme` per the existing light/dark map pattern). No
  per-mode duplicated variable.
- **Forced monospace** — every code surface gets `font-family: var(--font-mono)`
  in `globals.css`, so even if the user picks a non-mono display font the
  code keeps its columns aligned.
- **Defensive safety net** — incomplete community themes get the
  `kandown` defaults via `BASE_CODE_TOKENS`, so a theme that ships only
  the old 21 tokens still renders code legibly.
- **Preview in the customizer** — `ThemePreviewCard` gets a small
  `<pre><code>const x = 1;</code></pre>` sample. Not a live editor — just
  enough to judge the contrast.

## Out of scope

- Re-coloring Shiki's tokens per theme (would require a Shiki theme
  override and bundled asset; explicitly deferred per user direction).
- Per-language syntax palette (one palette covers all languages as today).
- Refactoring BlockNote's editor wrapper beyond the contrast fix.

## Notes

- Shiki spans have inline `style`; that's why the previous
  `color: foreground !important` on `pre` never reached the actual text.
  We lean into that: leave the spans alone, just control the background
  and the font.
- `pre` is forced to `background: hsl(var(--code-bg))`; Shiki's
  `pre { background: var(--shiki-light-bg) }` will be overridden by the
  `!important` so our themed background always wins.
- Token names follow the existing convention (`<role>` or
  `<role>-<modifier>`); no new prefix.
