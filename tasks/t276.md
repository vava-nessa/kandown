report: |
  A global `npm i -g kandown` swaps the files on disk under a daemon that keeps
  serving the web bundle it was compiled with. The web UI noticed and rendered a
  modal telling the user to go and run `kandown daemon refresh-all`: a chore
  handed to the one person who does not care which process serves which build.

  The daemon is the process that knows it is stale, so it is the one that acts.

  Changes
  - `scheduleDaemonSelfUpgrade` (src/cli/lib/daemon.ts): started by `daemon run`,
    it compares `getInstalledVersion()` (package.json on disk, re-read each time)
    against `getCurrentVersion()` (the constant compiled into this process).
    Installed ahead of running means an update landed underneath, and it spawns a
    detached `kandown daemon restart` that stops it by PID and brings up the new
    build on the same port. First check 15s after boot, then every 5 minutes.
  - Reuses the existing restart command rather than reimplementing the dance, so
    ownership checks, port reuse and metadata rewrite stay on one tested path.
  - Anti-loop guard: the restart carries `KANDOWN_DAEMON_UPGRADED_TO=<target>`.
    A dev checkout has a generated `version.ts` lagging a bumped `package.json`,
    which is indistinguishable from a pending upgrade and would respawn forever;
    a process that sees its own target still pending gives up after one attempt.
  - `UpdateNotificationBanner.tsx`: the stale-daemon modal is gone. That state now
    renders a thin bottom-right pill ("Finishing update to vX", no buttons), the
    poll tightens to 4s while it lasts, and the page reloads once the daemon
    reports the matching version so the client is not holding connections that
    died with the old process. The full modal is reserved for a real new release.
  - `.kandown/.gitignore` now covers `extensions/enabled.json` and `trust.json`,
    and `kandown init` writes that file for new projects. Both are documented as
    ignored at load time, so a tracked copy is a confusing no-op.

  Verified end to end on a live daemon: bumped package.json to 0.44.0 under a
  running 0.43.0 daemon, waited, and the PID changed on its own (21690 to 24956)
  with `KANDOWN_DAEMON_UPGRADED_TO=0.44.0` in the new process environment. Left
  it a further minute with `version.ts` still stale: the PID held, proving the
  guard stops the loop. After a rebuild the API reports current == running and
  `restartRequired: false`.

  Tests: 7 cases in src/cli/lib/__tests__/daemon-self-upgrade.spec.ts (fires on a
  newer install, never on a downgrade or a match, tags the restart, honours the
  guard, still upgrades when a newer version lands after a failed attempt, stops
  on dispose).

# Daemon self-heals after an update instead of nagging the web UI

The web view showed a modal after every update: *"The installed package is
vX, but this server is still on vY. Restart the daemon to finish the upgrade."*
Make it finish by itself, permanently, for every user.

## Subtasks

- [x] Daemon detects that the package on disk moved ahead of it
  report: `pendingUpgradeTarget()` compares the freshly-read package.json version
  against the constant compiled into the running bundle.
- [x] Daemon restarts itself onto the new build, on the same port
  report: spawns a detached `kandown daemon restart`, reusing the tested restart
  path rather than duplicating the stop/start/port dance.
- [x] Guard against an infinite respawn loop
  report: `KANDOWN_DAEMON_UPGRADED_TO` marks the target; one attempt per version.
  Covers the dev checkout where a stale `version.ts` can never catch up.
- [x] Replace the web modal with a self-clearing indicator
  report: thin pill, no buttons, 4s polling while it lasts, auto-reload when the
  daemon comes back current.
- [x] Stop local extension state from leaking into git
  report: `.kandown/.gitignore` covers `extensions/enabled.json` and `trust.json`;
  `kandown init` now writes that file for new projects.
