# Fix documentation Markdown copy buttons

## Context

The generated Markdown files are available and copy correctly when the modern
Clipboard API is granted. The documentation button has no fallback when that
API is missing or denied, even though command-copy buttons already support the
legacy browser path. This makes every docs copy button fail in affected
browsers and embedded webviews.

## Subtasks

- [x] Reproduce and isolate the failure path
  report: Verified the production Markdown endpoint and clipboard contents in Chromium, then confirmed that CopyPageButton calls navigator.clipboard directly while CopyCommand already handles denied or unavailable Clipboard APIs.
- [x] Share one resilient clipboard helper across both button types
  report: Added one bounded Clipboard API helper with a textarea fallback, then moved both command and documentation copy controls onto it.
- [x] Keep the Markdown cache correct across client-side navigation
  report: Cached Markdown is now keyed by its raw page URL, so a mounted docs button refetches content when the route changes.
- [x] Verify the modern, fallback, and stuck Clipboard API paths
  report: Reproduced the indefinitely pending Clipboard API after client navigation, then verified that the fixed button reaches Copied through the fallback instead of remaining on Copying.
- [x] Run website typecheck, build, and browser verification
  report: Website typecheck and production build pass. Browser verification passes on direct load and after Introduction to Installation client-side navigation.

## Completion report

Documentation Markdown copy buttons now share the resilient command-copy path,
recover from unavailable, rejected, or stalled Clipboard API writes, and fetch
the correct raw document after SPA navigation.
