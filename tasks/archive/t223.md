# Fix kandown launch and auto-update regressions

## Context

Running `kandown` must always land on the current web daemon for the project after a CLI update. Auto-update currently installs the package but can leave an already-running daemon serving the old bundle/version.

## Subtasks

- [x] Reproduce and inspect CLI/daemon/update flow
  report: Verified fresh `kandown --no-open` starts a daemon, then found the risky path: existing daemons are reused without checking their version after a CLI update.
- [x] Restart outdated project daemon automatically when launching `kandown`
  report: `startProjectDaemon` now treats missing/different daemon versions as stale, stops the old process safely, and starts the current CLI daemon.
- [x] Restart daemon after web/API update apply
  report: `/api/update/apply` now schedules a detached restart launcher after sending the success response, so Web UI-triggered updates switch to the updated daemon code.
- [x] Verify package manager installs the active global CLI
  report: Global update attempts now confirm the resolved `kandown --version` is at least the requested target version before reporting success.
- [x] Build and smoke-test launch/update behavior
  report: `pnpm build` passes. Smoke-tested fresh `kandown --no-open` auto-init/daemon start, simulated an old v0.33.2 daemon being replaced by the current v0.33.3 daemon, and verified `kandown update` reports up-to-date cleanly.
