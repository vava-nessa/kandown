# Bound project resolution so bare kandown prompts for init

## Context

Bare `kandown` in a directory without a project is supposed to show the TUI
init prompt ("No .kandown/ project found, create one?") and then auto-init.
The prompt flow exists and works (verified end-to-end in /tmp), but it almost
never triggers under `$HOME`: `resolveKandownDir` walks up every ancestor and
finds `~/.kandown/kandown.json` (a real home board vava keeps on purpose, in
the same directory the updater uses for its cache). Every stray launch
silently attaches to the home board instead of prompting.

Decisions (validated with vava):
- Stop the upward walk at the current git repository root, and never treat
  `$HOME` as a project root unless cwd IS `$HOME` (her home board keeps
  working when she runs `kandown` in `~` deliberately).
- Keep `~/.kandown` as her personal home board. The repo's own `.kandown/`
  (dogfooding) is unaffected.

## Subtasks

- [x] Bound `resolveKandownDir` upward walk at git root / $HOME
  report: candidate check is skipped when currentDir is $HOME and not the
  starting cwd; both .git and $HOME stop the ascent after their own
  candidate is evaluated, so a project sitting exactly at the repo root
  (or at $HOME by design) is still found.
- [x] Unify project-existence check on `kandown.json` in `cli.ts`
  report: bare-kandown branch now uses `existsSync(join(kandownDir, 'kandown.json'))`,
  matching `tui.tsx` and the resolver. A partial `.kandown/` no longer
  starts the daemon nor blocks the prompt.
- [x] Add regression tests for the boundary rules
  report: 5 specs in `resolve-kandown-dir.spec.ts` using `vi.doMock` on
  `node:os` to pin a per-test fake home. All pass; pre-existing
  archived-dep failure in board-reader.spec.ts is unrelated and out of scope.
- [x] Build, run tests, manual TTY verification
  report: `pnpm typecheck`, `pnpm test`, `pnpm codemap:check` all green;
  `pnpm build` regen the bundle; manual fake-TTY verified the prompt now
  appears in `~/kd-fix-b` (was hijacked before), the home board still
  loads from `~`, and dogfooding from `src/` still loads the repo board.

## Notes

Edge case: `$HOME` candidate is skipped during ascent but allowed when it is
the starting cwd, so a deliberate home board still resolves.
