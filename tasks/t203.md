# Fix multi-project daemon port clash

## Context

When `kandown` is launched from two different project folders, the second launch
**kills the first project's web daemon** and steals its port (2048). So only one
kandown could ever run at a time, even though the codebase was *designed* for one
daemon per project with automatic port incrementing.

## Root cause — THREE bugs found

### Bug 1: preemptive kill of other-project daemons

`listenOnAvailablePort()` had a top-level stale check that killed whatever
kandown sat on the default port, **regardless of project**:

```js
const staleInfo = detectStaleKandown(port, kandownDir);
if (staleInfo) {              // ← truthy even for OTHER projects
  process.kill(staleInfo.pid, 'SIGTERM');  // ← killed the other project's daemon
}
```

`detectStaleKandown()` returns `{ reason: null }` (= "don't touch, other project")
but the guard only checked object truthiness, not `reason`. The port-scan loop
below (which correctly skips other-project daemons) never ran because the kill
already freed port 2048.

## Fixes applied (`bin/kandown.js`)

`getDaemonStatus()` treated any failed HTTP fetch as proof the daemon was dead
and **deleted the metadata**. Node's `fetch` (undici) fails to recover from the
initial `ECONNREFUSED` window (fetches sent before the server binds) and reports
a healthy local server as down for seconds. Proven empirically: `curl` to the
fresh daemon answered from T+0.9s, but the parent's `fetch` returned null for the
entire 5s `waitForDaemon` window → "Daemon failed to start", orphaning a
perfectly healthy child.

### Bug 3 (surfaced live): browser-blocked (unsafe) port allocation

After the first two fixes shipped (v0.15.1), the multi-project path worked at the
*server* level — but launching `kandown` in a 2nd project still appeared broken
in the browser: Chrome/Firefox/Safari refuse to navigate to **port 2049**
(`net::ERR_UNSAFE_PORT`) because it is the well-known **NFS** port. The 2nd
concurrent project inherited 2049, so the daemon ran fine (curl answered) yet
the browser showed an error page. The first project (2048) kept working.

### Bug 2: parent↔child handshake destroyed healthy metadata

1. **Core kill fix** — `listenOnAvailablePort`: only kill when
   `staleInfo.reason` is truthy (same-project stale/zombie). Other-project
   daemons fall through to the scan loop (which already skips them).
2. **Handshake non-destructive** — `getDaemonStatus`: a transient fetch failure
   (`remote === null`) while the process is alive now returns non-running
   **without deleting metadata**, so retries can succeed. Metadata is only
   removed on a *real* conflict (response from a *different* daemon).
3. **TCP startup probe** — `waitForDaemon` now confirms startup via a raw
   `net.createConnection` probe (`isPortListening`) + `isProcessAlive`, instead
   of HTTP fetch. A TCP connect has no connection-pool state to poison, so it
   reliably tracks the real socket liveness the moment the server binds. The
   dir/pid ownership check still runs later via `getDaemonStatus()` for the
   status/stop commands.
4. **Port range** — consolidated duplicated constants (`DEFAULT_SERVE_PORT`/
   `MAX_SERVE_PORT` removed) and widened 2048–2060 (13) → 2048–2150 (103).
   `waitForDaemon` timeout bumped 5s → 8s for margin.
5. **Skip browser-unsafe ports** — `listenOnAvailablePort` now skips any port in
   Chromium/Firefox/Safari's restricted-ports list (`BROWSER_UNSAFE_PORTS`, from
   `net/base/port_util.cc`). In our range that is **2049 (NFS)**, which silently
   broke the 2nd concurrent project. A `--port` explicitly pointing at an unsafe
   port is now rejected with a clear message instead of a dead-looking daemon.
   `2048` (the default) is safe, so the primary project keeps its stable URL.

## Verification

Reproduced the original bug 100% (A→2048, launch B → A killed, B steals 2048).
After the fix, tested with 5 concurrent projects:

| Project | Result |
|---|---|
| A | ✅ 2048 (auto) |
| B | ✅ 2049 (auto) |
| C | ✅ 2050 (auto) |
| D | ✅ 2051 (auto-increment) |
| E | ✅ 2099 (`--port` forced) |

- All 5 daemons respond on their respective `/api/daemon` with correct
  `kandownDir`.
- Stopping/restarting one project leaves the others alive; the restarted one
  reclaims its previous port.
- `pnpm typecheck` passes; `node --check` on the CLI passes; no debug leftover.

## Design decision

Chose **Strategy A (multi-instance, each project its own port)** over a shared
multi-tenant daemon, because the web app accesses task data via the File System
Access API (per-tab handle) — the server only serves static HTML + a health
endpoint, so a mutualized server would be a big refactor for ~zero gain.

Port strategy: preferred 2048 + auto-increment on conflict (stable, bookmarkable).
