# Workflow and skill store

## Context

The north star, in the user's words:

> Je fais un projet, je tape `npm i kandown`, `kandown`, je choisis ensuite dans ma
> web UI un workflow et 2/3 plugins — ça m'a pris moins de 30 secondes et j'ai un
> système de tâches fiable et cadré.

Today a new kandown project is an empty board with default columns. Everything that
makes kandown *good with agents* — the instructions, the task protocol, the column
semantics, the review discipline — is knowledge that lives in this repository's head
and gets rebuilt by hand in every project. A catalog turns that knowledge into
something installable, and turns "kandown is a Markdown kanban" into "kandown is a
working agent workflow, chosen in one click".

This is the **content** half of the store. It shares the registry, the manifest and
the install UI with [t257](t257.md) — one system, one `type` field — but it carries
no executable code, which is why it is the half that can ship first and safely.

## What is installable

Four entry types, all data rather than code:

- **Agent skills** — Markdown instruction sets injected into `kandown work` and
  `.kandown/instructions.md`: a code-review protocol, a release runbook, strict TDD,
  a research loop. This is the type with the most leverage: it is what kandown
  already does best, made shareable.
- **Board templates** — a preset of columns, priorities, tags and seed tasks:
  Scrum, bug tracker, content calendar, thesis. Feeds `kandown init --template <x>`.
- **Command recipes** — reusable CLI sequences: create an epic with its subtasks,
  archive the sprint, generate a report. Effectively a macro system, and the type
  whose format is least obvious — specify it last.
- **Themes** — the theme engine already supports third-party presets through
  `registerCustomThemes` (`src/lib/theme.ts`). They need distribution, not code.

## The reference workflow, concretely

`https://github.com/snarktank/ai-dev-tasks` is the shape of thing to support, and
the entry to build the format against. It is three Markdown prompt files that
compose into one discipline:

1. `create-prd.md` — the agent interviews the user and writes a PRD for the feature.
2. `generate-tasks.md` — the PRD is broken down into a granular task list.
3. Work one sub-task at a time, stopping for human review between each.

Two observations that should shape the format, not just illustrate it:

**Its output is kandown's data model.** Step 2 produces a task list, which
ai-dev-tasks writes as a Markdown checklist because it has nowhere better to put it.
Kandown *is* that place. An installed workflow should not just drop prompt files in
a folder — the generate step should emit real `tasks/*.md`, and "one sub-task at a
time, with review" is already the subtask + `report:` protocol in
`AGENT_KANDOWN.md`. The interesting version of this feature is a workflow that
**binds to the task protocol**, not one that sits beside it. That is also the
argument for a smoke test in CI: the check is "does installing it produce a board
that `kandown doctor` still likes".

**Composition is the hard problem.** Kandown already injects its own protocol
through `kandown work` and `AGENT_KANDOWN.md`. An installed workflow carries its own
opinions about how to plan and when to stop, and two installed workflows will
contradict each other outright. Decide early whether skills **compose** (merged
sections, defined precedence) or are **exclusive** (one active workflow at a time,
like a theme). Exclusive is the honest default and the easiest to explain; the
30-second promise is "choose *a* workflow", singular.

## The open dilemma — curated in-house vs. plugging into existing catalogs

**To be decided before building. The most consequential question in this task.**

Two poles:

- **Plug into what exists.** Point at the established skill catalogs and the
  `awesome-*` lists for AI workflows and agents, and surface them inside kandown. A
  large library on day one, no content to write, no moderation queue.
- **Curate our own.** A hand-picked, tested, versioned catalog. Small, opinionated,
  and every entry actually works with kandown's task protocol.

**My recommendation: a hybrid, with the index owned by us.**

Aggregating live is the wrong default, because the promise being made is
*"30 seconds and I have a reliable, framed system"*. That promise is not about
volume, it is about the thing working the moment it lands. An upstream list is
written for humans to read, not for a machine to install: entries drift, formats
disagree, links rot, and a single broken install destroys the one thing this feature
sells. Proxying someone else's list also hands them silent write access to what
kandown recommends.

Concretely:

1. **We own `index.json`.** Every entry is pinned to a commit or a release tag, never
   tracked from a moving branch.
2. **We seed it from upstream** — an ingestion script proposes entries harvested from
   the well-known skill catalogs and awesome-lists as *pull requests*, with attribution
   and licence. Their breadth, our gate.
3. **Every entry is smoke-tested in CI** before it can merge: does it parse, does it
   install into a scratch project, does the resulting board still pass `kandown doctor`.
4. **Curation is the product.** Ten workflows that work beat four hundred links.
   Volume can come later from community PRs, on rails that already enforce the gate.

The counter-argument deserves recording: this is real ongoing maintenance work, and
it makes kandown responsible for content it did not write. If that upkeep is not
wanted, the honest alternative is not a live aggregator — it is a short, explicitly
in-house catalog with a "submit yours" link.

## Decisions already taken

Carried over from [t257](t257.md) and settled with the user:

- **One unified store** — a single registry and manifest with `type`
  (`plugin` | `skill` | `template` | `theme`), one install UI, one update path.
- **Registry = a GitHub repo with a JSON index**, entries submitted by PR.
- **Explicit opt-in network only** — the catalog is fetched when a human opens the
  store or runs a store command, never in the background. Invariant #5 holds.

## Decisions, 2026-08-01

- One exclusive workflow is active per project. Compatible skills remain additive.
- Store workflows are immutable. Customization creates a versioned local fork.
- Instruction detail (`caveman`, `standard`, `complete`) and task tracking cadence
  (`live`, `balanced`, `economy`) are independent settings.
- `kandown work` is compiled by one shared pure module used by the CLI, agent
  launcher, and Settings preview. Its immutable core cannot be removed.
- Project instructions live in `.kandown/kandown_work.md`.
- Board columns keep user-defined names and gain explicit semantic roles plus an
  optional instruction field included dynamically in `kandown work`.
- Workflows can ship any number of named Markdown task templates and one optional
  board preset. Applying the preset is explicit and previews task migrations.
- The initial built-in suite is Kandown Standard, Real Engineering, Guided Feature,
  Spec Driven, Long Run, and Diagnose & Fix. Names remain neutral and manifests
  attribute their primary inspirations.
- Community workflows are published from author-owned GitHub repositories. The
  store indexes approved repositories, reads GitHub metadata, installs pinned
  releases, and offers validated updates only after explicit user confirmation.

## Subtasks

- [x] **Resolve the curation dilemma above**: Kandown owns a curated repository index.
      Authors publish and evolve workflows in their own GitHub repositories. Initial
      inclusion is moderated; later releases are validated automatically and offered
      as explicit, diffable updates.
  report: Researched ten workflow families from 37 primary-source citations and saved
    the comparison in `docs/research/agent-workflow-patterns.md`. The six chosen
    built-ins cover small work, vertical delivery, guided discovery, specification,
    long-running execution, and diagnosis without relying on branded names.
- [ ] **Specify the skill format** — how an installed skill reaches an agent. It must
      compose with the existing `.kandown/instructions.md` and `AGENT_KANDOWN.md`
      generation rather than fight it. Decide composition vs. exclusivity (see above)
      before anything else in this sub-task.
- [ ] **Port `ai-dev-tasks` as the first workflow entry** — the reference
      implementation of the format, and the proof that a workflow can bind to the task
      protocol instead of merely living next to it: its generate step should create
      real `tasks/*.md`, and its review loop should map onto subtasks + `report:`.
- [ ] **Specify the board template format** — columns, priorities, tags, seed tasks;
      wire it to `kandown init --template <x>`. Reuse the existing `templates/`
      seeds as the first entry so the format is proven by the thing that already works.
- [ ] **Ship the theme entry type first** — themes are pure data, the engine already
      accepts third-party presets, and there is now a house theme to publish. The
      cheapest end-to-end proof that the registry, the install path and the store UI
      hold together.
- [ ] **Design the 30-second first run** — after `kandown init`, the board offers a
      workflow and a couple of add-ons. Must be skippable and never block a user who
      just wants an empty board.
- [ ] **Build the ingestion script** (if the hybrid is chosen) — harvest upstream
      catalogs, open PRs against `index.json`, carry attribution and licence.
- [ ] **Specify the command-recipe format last** — the least obvious of the four, and
      the one most likely to be cut. Do not let it hold up the other three.

## Notes

Sequencing worth defending: this task can ship entirely without [t257](t257.md).
It is data, so there is no runtime loading problem, no sandbox question and no
supply-chain exposure — and it validates the registry, the manifest and the install
UX that the plugin system then inherits. The recommendation was to build it first for
exactly that reason; the unified-store decision does not prevent it, as long as the
manifest is designed for all four types from the start.

Assigned to a human: the curation call is a product and editorial commitment, not an
implementation detail.
