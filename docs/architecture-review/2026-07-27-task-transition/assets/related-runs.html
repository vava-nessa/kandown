Policy concentrates in Rust. MLX and system remain Swift adapters (ADR cloud-tts-non-macos honored).

Problem

GenerationPipeline.swift hosts the canonical lifecycle (enqueue, chunk, cache lookups, language fallback, cap enforcement, cancel propagation) while suzu-tts-orchestrator already has queue/chunker/backend primitives in Rust but does not run. Two implementations drift; t089 cannot complete because the live policy lives outside the daemon.

Solution (plain English)

Move the speech lifecycle into one deep Rust module whose interface is the seam. Keep the MLX inference worker and AVSpeechSynthesizer adapter inside the Swift shell — they remain the only places that touch Metal and AVFoundation. macOS still runs MLX locally; non-macOS shells plug their backend behind the same seam, as ADR tech.adr.cloud-tts-non-macos already predicts.

Benefits

  • Locality · caps, cache hits and language fallback live next to the message store.
  • Leverage · every voice backend inherits the same lifecycle without rewriting it.
  • Depth · the shell adapter becomes shallow (talk to one interface); the deep module becomes the only test surface.
  • Deletion test · deleting the orchestration block from GenerationPipeline.swift changes no observable behaviour because that knowledge now lives behind the seam.

Dependency category

Ports & adapters · MLX and system voice are real local adapters; future cloud backends are remote-but-owned. Two adapters justify a port, per seam discipline.

Deletion test

Removing the duplicated orchestration from GenerationPipeline.swift is non-breaking once the seam exists — the implementation moves, behaviour does not.

ADR status

Aligned with tech.adr.rust-first-freeze and tech.adr.cloud-tts-non-macos. No conflict with current code; this is the planned finish of t089.

Decode lives once; WKWebView and mock are the two adapters that justify the seam.

Problem

Action shape, validation, and state contribution are re-encoded across SettingsSnapshot.swift, SettingsWebController.swift, AppSettingsModel.swift, AppSettingsController.swift, types.ts and mock.ts. The same 103+ action types live in two languages; one change ripples into four files, and no Settings contract test guards the seam.

Solution (plain English)

One deep module owns the action vocabulary, the decode/validate rules, the state contribution, and the error report. The WKWebView side becomes an adapter that forwards raw messages to the module and applies its result to the snapshot. The TS side keeps its mock.ts adapter and renders using only the deep module's outcome.

Benefits

  • Locality · one owner per action shape; one validator; one error format.
  • Depth · the bridge loses its parallel state; tests target the seam, not the switch.
  • Leverage · the mock adapter becomes a real test surface for the deep module instead of duplicating rules.
  • Deletion test · delete AppSettingsController's forwarding or mock.ts's validators — the deep module still answers, only the adapters thin out.

Dependency category

Ports & adapters · WKWebView (production) + mock (dev/test) are the two adapters that justify the seam.

Deletion test

Removing AppSettingsController forwarders or the mock validators does not lose any decode rule — the deep module is the only place it lives.

ADR status

Aligned with tech.adr.daemon-owns-state: shells project state, deep module projects nothing of its own.

One catalog, one aggregator; the subprocess stays the port (ADR preserved).

Problem

The 18-entry provider catalog is hand-mirrored in QuotaProviderScanner.allKnown and the TS mock.ts's allKnownProviders. Per-family aggregation logic sits next to the subprocess adapters rather than next to the catalog. New providers (Bedrock, Cursor, Augment just landed) cause three file edits and silent drift if one is missed.

Solution (plain English)

Promote the catalog and the per-family aggregator into one deep module behind the subprocess seam. The shell adapter exposes only the aggregator's output to Settings and the menubar gauge. The subprocess stays exactly where ADR tech.adr.quota-fetcher-subprocess requires it.

Benefits

  • Locality · catalog and aggregation sit together; new providers touch one file.
  • Leverage · both the menubar gauge and the Settings pane consume the same aggregated output.
  • Depth · the Swift and TS adapter ends become shallow projections.
  • Deletion test · deleting QuotaProviderScanner.allKnown or the mock catalog leaves Settings correct because the daemon now owns the canonical list.

Dependency category

Ports & adapters · the subprocess is the port (ADR-protected). Swift and TS are adapters; Rust holds the implementation.

Deletion test

Removing the duplicated catalogs (allKnown, allKnownProviders) is non-breaking because the deep module supplies the canonical list.

ADR status

Aligned with tech.adr.quota-fetcher-subprocess · the seam stays a subprocess, never embedded. Aligned with tech.adr.rust-first-freeze.

state.rs shrinks; the timer is no longer a leak from a foreign module.

Problem

state.rs (1.3k lines) holds the deferred-fallback timer whose lifecycle belongs to the session registry. sessions.rs and pending.rs cannot answer "what happens to a session when the user takes too long?" without paging through the global state file. Splitting state.rs by file is not the fix — the timer is the wrong owner.

Solution (plain English)

Move the deferred-fallback timer into sessions.rs next to the rest of the session lifecycle. The pending-ask registry stays single, as ADR tech.adr.pending-ask-registry requires. state.rs keeps persistence and SSE plumbing and stops carrying session-timer state.

Benefits

  • Locality · the timer sits next to the sessions whose policy it implements.
  • Depth · state.rs becomes a small coordination module instead of a god-module.
  • Deletion test · deleting the timer block from state.rs no longer risks losing the fallback rule, because the rule lives behind the sessions seam.

Dependency category

In-process · pure lifecycle logic, no I/O. Direct test through the new interface.

Deletion test

Removing the timer from state.rs while keeping the behaviour in sessions.rs changes no observable outcome.

ADR status

Aligned with tech.adr.pending-ask-registry · one registry remains. Aligned with tech.adr.daemon-owns-state · no state moves out of the daemon.

Top recommendation

Move the speech lifecycle into a Rust deep module — keep MLX & system as Swift adapters.

This is the candidate with the strongest fit to the documented ADRs (tech.adr.rust-first-freeze, tech.adr.cloud-tts-non-macos, tech.adr.daemon-owns-state) and the one that unblocks both t089 and t091. The other three are real wins, but they become safer to ship after the speech lifecycle is owned in one place.
